When a signed-in user opens the widget, you can tell opendesk who they are. Without verification, anyone could claim to be any user. With it, opendesk accepts the identity only when it comes with a proof that only your server can produce.

Each chat widget has its own secret. Sign with the secret of the widget that runs on that site: a session is verified only by the widget whose secret signed it.

Your server can prove a user's identity in two ways:

- **`user_token`**: a JWT signed with the widget secret that carries the user's id and an expiry. It stops working at its `exp`, at most 24 hours ahead by default, so a token copied from a page is of no use for long.
- **`user_hash`**: an HMAC of the user's id. It stays valid until you rotate the widget's secret.

Both keep working side by side. New setups should use `user_token`, and a widget can be set to accept nothing else (see [Require an expiring token](#require-an-expiring-token)).

<Steps>

1. **Get the widget's secret.** Open **Settings**, **Brands and widgets**, the brand, then the widget on its **Chat widgets** tab. Under **Identify signed-in users**, click **Rotate secret**. The new secret is shown once, so store it in your server's secrets. A new widget can also show its first secret right when you create it.

2. **Sign a token on your server** for the signed-in user, with one of the [examples below](#sign-a-user-token).

3. **Pass `user_token` to the widget**, together with the optional `email` and `name`, and a `refresh_user_token` function that gets a new token from your server. The widget sends them when it starts a session (`POST /v1/widget/session`).

<Aside type="danger" title="Keep the secret on the server">
Never put the widget secret in browser code, a mobile app or a public repository. Sign tokens on your server and send only the result to the page.
</Aside>

## Sign a user token

A `user_token` is a JWT signed with **HS256**, keyed with the widget secret, with these claims:

| Claim | |
| --- | --- |
| `user_id` | your stable id for the user, a string (an integer is read as its digits), up to 200 characters. Required |
| `exp` | when the token stops working, in Unix seconds. Required, and at most the widget's **Longest token lifetime** ahead: 24 hours unless you change it |
| `iat`, `nbf` | optional. A token issued or valid only after now is refused |

opendesk allows two minutes for a difference between your server's clock and its own.

<Tabs syncKey="lang">
<TabItem label="Node">

```js
import jwt from 'jsonwebtoken';

export function userToken(userId) {
  return jwt.sign({ user_id: String(userId) }, process.env.OPENDESK_WIDGET_SECRET, {
    algorithm: 'HS256',
    expiresIn: '24h',
  });
}
```

</TabItem>
<TabItem label="Python">

```python
import os
import time

import jwt  # PyJWT

def user_token(user_id: str) -> str:
    now = int(time.time())
    return jwt.encode(
        {"user_id": str(user_id), "iat": now, "exp": now + 24 * 3600},
        os.environ["OPENDESK_WIDGET_SECRET"],
        algorithm="HS256",
    )
```

<TabItem label="Go">

```go
package widget

import (
	"os"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

func UserToken(userID string) (string, error) {
	now := time.Now()
	return jwt.NewWithClaims(jwt.SigningMethodHS256, jwt.MapClaims{
		"user_id": userID,
		"iat":     now.Unix(),
		"exp":     now.Add(24 * time.Hour).Unix(),
	}).SignedString([]byte(os.Getenv("OPENDESK_WIDGET_SECRET")))
}
```

## Pass it to the widget

```js
opendesk('identify', {
  user_token: '<token from your server>',
  // Optional: a function that answers a new token from your server.
  refresh_user_token: () => fetch('/opendesk-token').then((r) => r.text()),
  email: 'ada@example.com',
  name: 'Ada Lovelace',
});
```

`user_id` can be left out: the token carries it. When you send it too, it must be the token's. With a `user_token`, a `user_hash` sent along is not read.

`refresh_user_token` is called by the widget, never by opendesk, so it can use your page's own sign-in to reach your server. The widget calls it:

- before it starts or resumes a session, when its token expires within a minute, or when you passed `refresh_user_token` without a `user_token`;
- when the API answers `401 user_token_expired`, and then tries again once with the new token.

## When a token expires

A token starts a verified session; it does not have to stay valid for the session to carry on. When the page sends an expired token together with the visitor token of the session that token verified on that browser, for the same user, the session continues, up to the 30 days a verified session lives. So a page that stays open for longer than its token keeps its chat, even without `refresh_user_token`.

Anything else needs a token that has not expired, and answers `401 user_token_expired` otherwise: starting a session in a new browser, verifying an anonymous session, or switching the session to another user. A copied token is therefore of use only until its `exp`.

## Require an expiring token

Under **Identify signed-in users**, turn on **Require an expiring token** once every page that loads the widget sends `user_token`. From then on the widget refuses `user_hash` with `401 user_token_required`, on new sessions and on sessions it verified before, and signed-in users are verified only by tokens. Anonymous visitors are not affected.

**Longest token lifetime**, next to it, sets how far ahead a token's `exp` may be, from 1 hour to 30 days. A token whose `exp` is further ahead is refused with `401 invalid_user_token`. Keep it short: it is how long a copied token can start a session.

## Send the user's company and attributes

With a verified identity you can also send the account the user belongs to and a few attributes, so agents see who a chat comes from without asking:

```js
opendesk('identify', {
  user_token: '<token from your server>',
  email: 'ada@example.com',
  company: { id: 'acct-9' },
  fields: { widget_plan: 'pro', widget_seats: 12 },
});
```

- **`company.id`** is your own id for the account. opendesk links the contact to the company whose external id it is. Set that id on the company first, with `external_id` in the [companies API](/api/resources/contacts/). The widget never creates a company or changes its name or domain, since the token or hash proves only who the user is, and an id no company has is ignored.
- **`fields`** set the contact's [custom fields](/guides/labels-and-custom-fields/) by key. Only fields whose key starts with `widget_` are set: create `widget_plan` as a contact field first, and anything else, or a value that does not fit its field, is ignored. The values come from your page, so keep to this prefix only the fields you want the widget to fill, such as a plan name or a seat count.
- When something changes without a page load, call `opendesk('update', { … })` with the new values. It updates the contact without starting a new chat session. The widget keeps the `user_token` or `user_hash` it has, so you only need to send one again when it changed.
- Visitors without a verified identity are anonymous: `company` and `fields` are ignored.

## Use a user hash

A `user_hash` needs no JWT library, and it is what earlier setups use. It is:

```
user_hash = hex( HMAC-SHA256( key = widget_secret, message = user_id ) )
```

A session that sends a valid `user_hash` for its `user_id` is marked **verified**, and its conversations attach to the contact with that external id. Pass both to the widget:

```js
opendesk('identify', { user_id: '42', user_hash: '<hmac from your server>', email: 'ada@example.com' });
```

<Tabs syncKey="lang">
<TabItem label="Node">

```js
import { createHmac } from 'node:crypto';

export function userHash(userId) {
  return createHmac('sha256', process.env.OPENDESK_WIDGET_SECRET)
    .update(String(userId))
    .digest('hex');
}
```

</TabItem>
<TabItem label="Python">

```python
import hashlib
import hmac
import os

def user_hash(user_id: str) -> str:
    secret = os.environ["OPENDESK_WIDGET_SECRET"].encode()
    return hmac.new(secret, str(user_id).encode(), hashlib.sha256).hexdigest()
```

</TabItem>
<TabItem label="Go">

```go
package widget

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"os"
)

func UserHash(userID string) string {
	mac := hmac.New(sha256.New, []byte(os.Getenv("OPENDESK_WIDGET_SECRET")))
	mac.Write([]byte(userID))
	return hex.EncodeToString(mac.Sum(nil))
}
```

</TabItem>
<TabItem label="PHP">

```php
<?php
function user_hash(string $userId): string {
    return hash_hmac('sha256', $userId, getenv('OPENDESK_WIDGET_SECRET'));
}
```

</TabItem>
<TabItem label="Ruby">

```ruby
require "openssl"

def user_hash(user_id)
  OpenSSL::HMAC.hexdigest("SHA256", ENV.fetch("OPENDESK_WIDGET_SECRET"), user_id.to_s)
end
```

For the secret `test-secret` and user id `42`, every example above must return the same 64-character lowercase hex string. Compare your output across languages, or with:

```sh
printf '42' | openssl dgst -sha256 -hmac 'test-secret'
```

A hash has no expiry: it proves the user's id until you rotate the secret. To move to tokens, send `user_token` from every page, then turn on [Require an expiring token](#require-an-expiring-token).

## Errors

| Code | Status | When |
| --- | --- | --- |
| `invalid_user_token` | 401 | The token is not an HS256 JWT signed with this widget's secret, lacks `user_id` or `exp`, has an `exp` further ahead than the widget allows, is not valid yet, or carries another `user_id` than the one sent |
| `user_token_expired` | 401 | The token's `exp` has passed, and the request would start or verify a session. Sign a new one |
| `user_token_required` | 401 | The widget requires an expiring token and the request sent `user_id` or `user_hash` without one |
| `invalid_user_hash` | 401 | The hash does not match `user_id` with this widget's secret |

## Several widgets

All the widgets of a workspace share one set of user ids: a verified `user_id` is the same contact whichever widget verified it. So:

- Use the same user ids on two sites only when they are the same people, such as one account system behind both.
- Keep every widget's secret as safe as the others: each one vouches for the same ids.
- A visitor who was verified on one widget is verified on another only when that widget's own secret signed the same `user_id`. Otherwise they start there as a new, anonymous visitor.

## Tips

- Use a stable id that never changes for the user, such as your database primary key, not an email address.
- Send the id as a string. A hash is computed over its exact bytes.
- Sign tokens when the page loads, or from `refresh_user_token`, never ahead of time in bulk.
- When a user signs out of your product, call `opendesk("shutdown")`. It ends the widget session on the server too, so the next visitor on the same browser does not see their conversations.
- A verified session is never picked up again without a token or hash: a page that loads the widget without one starts an anonymous visitor. A verified session also ends 30 days after it started, and the next page that verifies the user starts a new one without asking them anything.
